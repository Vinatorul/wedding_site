# Деплой на виртуалку с Docker и Caddy

Скрипт `scripts/deploy-vm.py` размещает приглашение за уже работающим Caddy. Для сайта создаётся отдельный контейнер без открытых наружу портов. Скрипт добавляет в общий Caddyfile только блок нового домена и применяет его через `caddy reload`. Остальные сайты, контейнер прокси и его сертификаты остаются на месте.

Нужны Linux, Git, Python 3.10 или новее и работающий Docker. Общий Caddy должен быть запущен в контейнере, подключён к Docker-сети и читать Caddyfile из файла или каталога, смонтированного с виртуалки. Для сборки контейнера приглашения нужен доступ к Docker Hub и публичному PyPI: используется официальный образ `python:3.13-slim`, зависимости устанавливаются с `https://pypi.org/simple`.

Страницу и API анкеты обслуживает Gunicorn на внутреннем порту 8000. Caddy передаёт ему запросы через Docker-сеть; порт на виртуалке не открывается. Node.js и npm для деплоя не нужны. Если используешь `npx` для правок проекта, `.npmrc` задаёт публичный `https://registry.npmjs.org/`.

## Подготовка

Выполняй команды на виртуалке в Bash. Сначала клонируй репозиторий под своим обычным пользователем:

```sh
git clone https://github.com/Vinatorul/wedding_site.git
cd wedding_site
```

Если репозиторий закрытый, заранее настрой на виртуалке доступ к GitHub, например SSH-ключ, и используй SSH-адрес репозитория. Не записывай токены или приватные ключи в файлы проекта.

Посмотри список контейнеров:

```sh
sudo env DOCKER_API_VERSION=1.43 docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
```

Найди Caddy, который обслуживает порты 80 и 443. Заполни параметры в терминале; они не попадут в репозиторий:

```sh
read -rp 'Домен сайта без https://: ' SITE_DOMAIN
read -rp 'Имя общего Caddy-контейнера: ' PROXY_CONTAINER
sudo env DOCKER_API_VERSION=1.43 docker inspect "$PROXY_CONTAINER" \
  --format '{{json .NetworkSettings.Networks}}'
sudo env DOCKER_API_VERSION=1.43 docker inspect "$PROXY_CONTAINER" \
  --format '{{json .Mounts}}'
read -rp 'Docker-сеть общего прокси: ' PROXY_NETWORK
read -rp 'Полный путь к Caddyfile на виртуалке: ' CADDY_FILE
```

В первом выводе возьми имя сети, во втором — `Source` у Caddyfile. Если смонтирован каталог, допиши имя файла внутри него. Параметр `--caddyfile` принимает путь на виртуалке; путь внутри контейнера скрипт определит сам.

В этих командах `DOCKER_API_VERSION=1.43` обеспечивает совместимость с Docker на текущей виртуалке. На другом сервере с более новым Docker этот параметр можно убрать.

## Первый запуск

```sh
sudo env DOCKER_API_VERSION=1.43 python3 scripts/deploy-vm.py \
  --domain "$SITE_DOMAIN" \
  --network "$PROXY_NETWORK" \
  --proxy-container "$PROXY_CONTAINER" \
  --caddyfile "$CADDY_FILE"
```

По умолчанию контейнер называется `wedding-site-web`, а файлы хранятся в `/srv/wedding-site`. Если эти имена уже используются, передай свободные через `--container` и `--deploy-root`. Каталог деплоя должен быть отдельным, вне репозитория.

Скрипт копирует `dist/` в новый каталог `releases/`, собирает образ приглашения и запускает свой контейнер. Каталог деплоя монтируется в него только для чтения, а `data/` — отдельно для записи в `/data`. Контейнер работает под UID 10001; скрипт выдаёт ему доступ к этому каталогу.

Ответы сохраняются в `/srv/wedding-site/data/rsvp.sqlite3`, вне `releases/`. Смена релиза и пересоздание контейнера сохраняют эту базу. При другом `--deploy-root` база лежит в его подкаталоге `data/`.

После переключения ссылки `current` скрипт проверяет `/api/health`, включая доступ к SQLite. Перед изменением общего Caddyfile он сохраняет копию в `config-backups/`. Затем проверяет конфигурацию Caddy и применяет её без остановки прокси.

Если домен уже настроен вне блока этого скрипта или имя контейнера занято другим приложением, запуск остановится с пояснением. При ошибке проверки или применения конфигурации скрипт возвращает прежний `current` и контейнер и пытается восстановить настройку Caddy. База с ответами остаётся на месте. Если сам откат не удался, это отдельно появится в выводе; копия Caddyfile находится в `/srv/wedding-site/config-backups/`.

Общий Caddyfile обновляется на месте. Это нужно, когда Docker монтирует отдельный файл: замена файла через `mv` или редактор с атомарным сохранением может оставить прокси на старой версии.

## Игра по адресу `/rover/`

Скрипт может добавить игру на тот же домен: приглашение останется по `/`, а игра откроется по `/rover/`. Сначала обнови контейнер игры до версии, которая поддерживает этот путь. Возьми имя контейнера и его внутренний порт из настроек игры.

Общий Caddy должен уже быть подключён к Docker-сети игры. Посмотри его сети командой из раздела подготовки. Сеть игры может отличаться от `PROXY_NETWORK`, через которую работает приглашение. Если подключения нет, сначала настрой его отдельно: скрипт проверяет сеть, но не подключает её и не перезапускает прокси.

Для включения маршрута задай ещё две переменные и передай оба параметра:

```sh
read -rp 'Контейнер игры и внутренний порт, например rover-rally-app:8787: ' ROVER_UPSTREAM
read -rp 'Docker-сеть игры: ' ROVER_NETWORK
sudo env DOCKER_API_VERSION=1.43 python3 scripts/deploy-vm.py \
  --domain "$SITE_DOMAIN" \
  --network "$PROXY_NETWORK" \
  --proxy-container "$PROXY_CONTAINER" \
  --caddyfile "$CADDY_FILE" \
  --rover-upstream "$ROVER_UPSTREAM" \
  --rover-network "$ROVER_NETWORK"
```

`--rover-upstream` принимает имя контейнера и порт от 1 до 65535, без схемы URL и пути. При переходе с `/rover` на `/rover/` сохраняются параметры комнаты и экрана. Caddy передаёт запросы игре без префикса `/rover`, а остальные запросы — приглашению.

После деплоя проверь `https://<твой-домен>/rover/?view=host`: создай комнату, подключи игрока и проверь старт и кнопку «ГАЗ». Обновление приглашения не обновляет контейнер игры.

Следующие деплои сохраняют маршрут и сеть из собственного блока в Caddyfile, даже если не передавать параметры `--rover-*`. Чтобы сменить контейнер или сеть игры, снова передай оба параметра. Если прежний маршрут не удаётся прочитать, скрипт остановится до изменений: проверь его блок в Caddyfile. Не удаляй из него комментарий `rover-network`, который нужен для проверки сети при следующих запусках.

## Проверка домена и HTTPS

DNS-запись A должна указывать на публичный IPv4 виртуалки. Если есть AAAA, она тоже должна вести на этот сервер по доступному IPv6. Снаружи должны быть доступны порты 80 и 443, а у общего Caddy должны сохраняться данные сертификатов между запусками. При добавлении домена Caddy сам получает сертификат — см. [условия автоматического HTTPS](https://caddyserver.com/docs/automatic-https).

После деплоя проверь сайт:

```sh
dig +short A "$SITE_DOMAIN"
dig +short AAAA "$SITE_DOMAIN"
curl --fail --head "https://${SITE_DOMAIN}/"
```

Проверка внутри скрипта подтверждает работу контейнера сайта. Внешний DNS и выдачу сертификата проверяет последняя команда. Если HTTPS не открылся, посмотри логи общего прокси и сайта:

```sh
sudo env DOCKER_API_VERSION=1.43 docker logs --tail 100 "$PROXY_CONTAINER"
sudo env DOCKER_API_VERSION=1.43 docker logs --tail 100 wedding-site-web
```

Если передавал другое имя через `--container`, подставь его и здесь.

## Обновление

В каталоге репозитория выполни:

```sh
git pull --ff-only
sudo env DOCKER_API_VERSION=1.43 python3 scripts/deploy-vm.py \
  --domain "$SITE_DOMAIN" \
  --network "$PROXY_NETWORK" \
  --proxy-container "$PROXY_CONTAINER" \
  --caddyfile "$CADDY_FILE"
```

Используй те же параметры, что при первом запуске, включая `--container` и `--deploy-root`, если менял их. В новом сеансе терминала снова задай четыре переменные из раздела подготовки. Можно сохранить параметры в собственный файл на виртуалке вне репозитория; скрипт сам такие файлы не читает.

Повторный запуск пересоздаёт только контейнер приглашения и обновляет свой блок в Caddyfile. База, старые релизы, образы и резервные копии остаются на месте. Если скрипт другого приложения заменил весь общий Caddyfile, повторный деплой приглашения вернёт его блок. Для восстановления удалённого маршрута игры передай также `--rover-upstream` и `--rover-network`. Чтобы это не повторялось, скрипты других приложений тоже должны сохранять соседние домены.

## Выгрузка ответов

На виртуалке из каталога репозитория выполни:

```sh
(
  umask 077
  sudo python3 scripts/export-rsvp.py \
    --database /srv/wedding-site/data/rsvp.sqlite3 > "$HOME/wedding-answers.csv"
)
```

Если менял `--deploy-root`, подставь путь к базе в его каталоге `data/`. `sudo` нужен для чтения базы; CSV создаётся от твоего пользователя. `umask 077` закрывает доступ другим пользователям к новому файлу.

CSV содержит столбцы `id`, `created_at`, `name`, `companion`, `attendance`, `drink`, `food`. Время записано в UTC. Файл использует UTF-8 с BOM для Excel и сохраняет запятые, кавычки и переносы строк в ответах.

В столбце `attendance` остаются значения из анкеты:

| Значение   | Выбранный вариант |
| ---------- | ----------------- |
| `yes`      | С утра до вечера  |
| `ceremony` | Только роспись    |
| `buffet`   | К фуршету         |
| `banquet`  | К началу банкета  |
| `no`       | Не смогу          |

Выгрузка не меняет ответы. Если их пока нет, CSV содержит только заголовок. Если база отсутствует или повреждена, скрипт завершится с ошибкой. Публичной страницы или API для чтения ответов нет.

## Возврат прежних файлов сайта

Выбери прежний каталог в `/srv/wedding-site/releases/` и переключи ссылку. В команде ниже замени `ИМЯ_РЕЛИЗА` на имя нужного каталога:

```sh
sudo python3 - /srv/wedding-site ИМЯ_РЕЛИЗА <<'PY'
import os
from pathlib import Path
import sys

root = Path(sys.argv[1])
release = root / "releases" / sys.argv[2]
if release.parent != root / "releases" or not (release / "index.html").is_file():
    raise SystemExit("Не найден выбранный релиз")
temporary = root / ".current-rollback"
temporary.symlink_to(f"releases/{release.name}")
os.replace(temporary, root / "current")
PY
```

Если каталог деплоя другой, замени и `/srv/wedding-site`. Для возврата файлов перезапуск контейнера или Caddy не нужен. Этот способ возвращает только файлы сайта; код API, база и настройка прокси остаются текущими.

Контакты команды и дресс-код требуют уточнения перед рассылкой приглашения.

## Локальная проверка

Создай `.venv` и установи зависимости, как в [README](README.md). Затем запусти проверки деплоя, анкеты и выгрузки:

```sh
.venv/bin/python -m unittest discover -s tests -p test_deploy_vm.py -v
.venv/bin/python -m unittest discover -s tests -p '*rsvp*.py' -v
```

Проверки используют настоящие временные файлы и SQLite; команды Docker моделируются. Для проверки живого Caddy нужен запуск на сервере.
